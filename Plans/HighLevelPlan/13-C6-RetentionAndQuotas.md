# C6. Retention and quotas

**Phase C — Backups in Hive** · Engine, 1–2 sessions

References like §10 point to [00-Info.md](00-Info.md). Look at `../site-backups/src/Backup/ApplyRetentionCommand.php` and `ApplyMonthlyBackupCommand.php` for what this replaces.

Retention must never remove the wrong snapshot (AGENTS.md). This slice is mostly tests.

- **Tiers** (§10): which snapshots a job keeps, as a pure function of its snapshots, their dates and its tiers. Daily tiers count days that have a snapshot, not calendar days, so a long outage never ages out history. Settle the exact rules: several runs on one day, month boundaries, and partial snapshots. A failed run's partial folder goes once a newer snapshot is complete. Choose defaults (§19).
- **Counting space** as it's used on the drive: files are grouped by inode, so a file hard-linked into several snapshots counts once. For each snapshot, how much removing it would free, and the total for each server. Kept in the catalog, and recounted only where a run or removal changed something, since a full recount of large trees over USB could take hours.
- **Quotas** (§10): when a server is over, its oldest daily snapshots are removed first, across all its jobs, until it fits. Monthly snapshots and the newest complete snapshot of each job are never removed for a quota. If it still doesn't fit, the server is marked over quota, for E2 to email about.
- **Lowering a quota or tiers:** nothing is removed because of the change until it's confirmed (D4)
- **Defaults:** C1 takes tiers and a quota with every job and server, and allows no quota. Choose the defaults D2 offers, and whether no quota stays allowed.
- **After a restore:** retention and quotas don't run until you confirm in Beekeeper (F3)
- **Removing safely:** a snapshot is removed only if it's in the catalog, its real path is inside its job's folder on the backup drive, and nothing is writing to it. It's renamed first, so a restart in the middle finishes the removal instead of leaving half a snapshot. Folders copied from servers without write permission get it back before removal. Symbolic links inside a snapshot are removed, never followed.
- **When it runs:** after each run, and once a day
- **Logging and the job log:** what was removed and why, and how much space it freed

- **From C3:** a partial can be left behind for good, besides a failed run's: when the job's directories changed since, the next run starts a new partial instead of picking it up. Snapshots are in the `snapshot` table with their drive UUID and folder names. A folder a server sent without write permission was writable on the drive in C3, since `--fake-super` keeps the server's mode in an attribute instead. Check files and deeper trees before relying on it.

## Tests

- Tiers keep exactly the right snapshots across days, months, several runs a day and daylight saving changes
- A job that failed for 30 days keeps the same daily snapshots it had when it started failing
- Space counted for hard-linked trees in temporary folders matches what removing them frees
- The quota never removes a monthly snapshot or the newest complete snapshot of any job, and marks the server over quota when that's all that's left
- Nothing outside the job's folder is ever removed, including through a symbolic link, `..` in a name, or a catalog entry pointing elsewhere
- A snapshot being written is never removed
- A snapshot with read-only folders is removed completely
- A removal interrupted halfway is finished on the next start

**Decisions (2026-11-06):**

- **Tiers** (`Retention/TierResolver`): days and months are the Hive Mac's, and both count only when they have a complete snapshot, so a long outage ages out no monthly history either (§10). Each kept day and month keeps its newest snapshot, so a job that runs several times a day keeps only the last of each earlier day. The newest complete snapshot is always kept. A partial that started before the newest complete snapshot completed is removed, since no run will pick it up, including C3's partials left after the job's directories changed. Complete snapshots are ordered by when they completed, which C3's link-dest now uses too, since a partial picked up days later completes after snapshots that started after it.
- **Defaults:** `RetentionTiers.suggested` is 30 daily and 12 monthly, for D2 to offer. No quota stays allowed, and is the default for a new server.
- **Counting space** (`Retention/DriveFolder`, `SnapshotSpaceCounter`): a walk opened through file descriptors that never follows a link, counting `st_blocks` by inode. What a snapshot frees is the space of files with no link outside it (`snapshot.freesBytes`). A job's space on a drive (`jobSpace.usedBytes`) counts each file once. After a run only the snapshot it wrote is uncounted, and adding what only it links to keeps the job's space exact without walking the others. A picked-up partial leaves its job's space at the start of the run and is counted again at the end. When more than one snapshot of a job is uncounted, or its space is unknown (the first pass after updating, a folder gone by hand), the whole job is counted once. A removal takes off what the snapshot freed, measured just before, and marks its nearest snapshots' `freesBytes` for a recount. Folders report no blocks on APFS, so the counts leave out folder metadata.
- **Quotas:** a server's use is the sum of its jobs' space on the drive. Snapshots of removed jobs don't count, and stay. Over quota, the oldest snapshots kept only by a daily tier go first across all the server's jobs, one at a time, each taking off what it measured, until the server fits. Still over, the server is marked in `overQuotaServer` with the date it first went over, cleared once it fits or has no quota. The quota waits while one of the server's jobs runs, or while a job's space isn't counted.
- **When it runs:** on the job queue, so never during a run: after each run, for that run's server, and a pass over everything once a day, which the scheduler asks for on its first check after Hive starts. A pass skips a job with a run going, and stops between steps when Hive stops.
- **Removing safely** (`SnapshotRemover`): only a catalog entry for the located drive whose server and job folders are its job's own, whose name is a snapshot's, and whose folder is a real folder opened without following links inside the job's folder, which is opened the same way from the drive's `Hive` folder. Every name is a single name, never a path. The catalog marks the snapshot `removing` with what it frees and why, then the folder is renamed `<folder>.removing` with `RENAME_EXCL`, then removed through descriptors: links are unlinked, folders missing their owner's permissions get them back (folders are never hard linked, so no other snapshot changes), and nothing crosses to another volume. A pass first finishes any removal left `removing`, and takes its space off once. A folder already gone is forgotten. Catalog entries pointing outside their job's folders are left alone, and never count toward its tiers.
- **Lowering a quota or tiers:** retention applies the stored values at its next pass. D4 refuses a lowering change without confirmation in the write transaction, which is what keeps anything from being removed before it's confirmed.
- **After a restore:** `hive.retentionPausedSince`, for F3 to set and clear. While it's set a pass counts but removes nothing and leaves quota marks alone.
- **The job log:** each job a pass removes something from gets one entry, with each snapshot, its date, why (`outsideTiers`, `replacedPartial`, `quota`), and the bytes it freed, plus any it couldn't remove and why. `GET /job-log` now gives `JobLogEntry`, either `.run(RunLogEntry)` (C5's entry, renamed) or `.removal(RemovalLogEntry)`, from the same table with a `kind` column. The system log has counts, bytes and durations, never paths or names.

**Result (2026-11-06):** the tests pass, including tiers across days, month and year ends, several runs a day, both daylight saving changes in New York's time zone, and a job failing for 30 days; counts matching a count the long way and what removing frees, for linked trees and for snapshots the bundled rsync made; quotas across jobs; and every refusal. With the development daemon and the `Hive C4 Drive` image, Example site's newest snapshot was copied with hard links into eight snapshots dated 14 September to 5 November, each with a 1 MB file of its own, and added to the dev store's catalog by hand. On start the daemon counted Example site at 8,818,688 bytes, the same as a count of every inode on the drive, and removed Postgres's earlier snapshot from the same day. With the test server's quota at 6,500,000 bytes through the Developer window, Run Now's pass removed the oldest three daily snapshots (5 October, 1 and 2 November, 1,048,576 bytes each) and the earlier snapshot from the same day, and the server fit. With the quota at 1 byte, the startup pass removed 3 and 4 and 5 November, kept 14 September and 27 October as monthly and the newest, and marked the server over quota. Hive said 3,145,728 bytes, and `df` showed 3,158,016 freed, the difference being folder metadata. The job log listed each snapshot with its reason and bytes. The copies dated 14 September and 27 October were then removed by setting the monthly tier to 0, and the tiers and quota were put back.

**Done when:** the tests pass, and on the test drive, setting the test server's quota below what it uses removes its oldest daily snapshots, keeps the monthly and newest ones, and frees the space Hive said it would.
